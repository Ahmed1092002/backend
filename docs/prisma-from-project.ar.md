# ‏دليل Prisma من مشروع Mini ERP

‏الدليل ده معمول عشان تفهم Prisma من الكود اللي عندك، مش تحفظ أوامر. اقرأ جزء صغير وجرّب تجاوب السؤال قبل اللي بعده. الأمثلة من المشروع الحالي؛ الأوامر الموضحة للتعلّم، وما اتنفذتش أثناء كتابة الدليل.

## ‏1. المشكلة التي تحلها Prisma

‏عندنا PostgreSQL، وهي قاعدة البيانات اللي بتحفظ المنتجات والمستخدمين والطلبات. PostgreSQL بتفهم SQL: لغة لقراءة البيانات وتعديلها. في Node.js نحتاج طريقة نتصل بها ونرسل طلبات لقاعدة البيانات ونستقبل النتائج.

‏Prisma أدوات بتساعدنا نوصف البيانات ونستخدمها من TypeScript. في المشروع عندنا ثلاثة أجزاء مهمة:

1. ‏⁦`prisma/schema.prisma`⁩: وصف الـmodels وإعداد الاتصال وطريقة توليد العميل.
2. ‏⁦`prisma/migrations/`⁩: تاريخ تغييرات قاعدة البيانات في ملفات SQL.
3. ‏Prisma Client: كود مُولَّد بنستخدمه في التطبيق، زي ⁦`prisma.product.findUnique(...)`⁩.

‏PostgreSQL هي اللي تخزن البيانات وتنفذ الاستعلامات. Prisma Client يرسل لها الاستعلام ويرجع النتيجة. الـschema وحده لا يغيّر قاعدة البيانات بمجرد حفظ الملف.

‏**فكر:** لو أغلقت تطبيق Node، فين بيانات المنتجات؟ في PostgreSQL، طالما تخزين قاعدة البيانات ما اتمسحش.

## ‏2. كيف يعرف التطبيق قاعدة البيانات؟

‏من ⁦`prisma/schema.prisma`⁩:

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

‏⁦`generator`⁩ يحدد طريقة توليد Prisma Client. و⁦`datasource`⁩ يحدد نوع قاعدة البيانات وعنوان الاتصال. ⁦`env("DATABASE_URL")`⁩ يقرأ العنوان من متغير بيئة؛ مش مكتوب كقيمة ثابتة في الملف. العنوان ممكن يختلف بين التشغيل المحلي وداخل Docker. لا تشارك قيمته لو فيها كلمة سر.

‏في ⁦`src/database/prisma.ts`⁩:

```ts
import { PrismaClient } from "@prisma/client";

export const prisma = new PrismaClient();
```

‏السطر الأول يستورد العميل المُولَّد، والثاني ينشئ نسخة يستخدمها التطبيق. باقي الملفات تستورد ⁦`prisma`⁩ بدل إنشاء عميل جديد لكل request؛ إنشاء نسخ كثيرة قد يؤدي لاتصالات أكثر من اللازم بقاعدة البيانات.

‏**فكر:** هل ⁦`new PrismaClient()`⁩ هو قاعدة البيانات نفسها؟ لا، هو العميل الذي يستخدمه التطبيق للتواصل معها.

## ‏3. قراءة model المنتج

‏من ⁦`prisma/schema.prisma`⁩، جزء من الـmodel الحقيقي:

```prisma
model Product {
  id        String   @id @default(uuid())
  name      String
  price     Decimal  @db.Decimal(10, 2)
  stock     Int      @default(0)
  imagePath String?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

‏الـmodel وصف لكيان نتعامل معه؛ ⁦`Product`⁩ مرتبط بجدول المنتجات. الحقل مثل عمود في الجدول، والسجل مثل صف يمثل منتجًا واحدًا.

- ‏⁦`id String`⁩: معرف نصي. ⁦`@id`⁩ يجعله المفتاح الأساسي، أي يميز كل صف. ⁦`@default(uuid())`⁩ يولد معرفًا تلقائيًا عبر Prisma عند عدم إعطائه.
- ‏⁦`name String`⁩: اسم مطلوب.
- ‏⁦`price Decimal @db.Decimal(10, 2)`⁩: سعر عشري، وتحديد PostgreSQL يسمح بعشرة أرقام إجمالًا، منها رقمان بعد العلامة.
- ‏⁦`stock Int @default(0)`⁩: عدد صحيح وقيمته الافتراضية صفر إذا لم تُرسل قيمة.
- ‏⁦`imagePath String?`⁩: علامة ⁦`?`⁩ تعني أن القيمة يمكن أن تكون ⁦`null`⁩.
- ‏⁦`createdAt @default(now())`⁩: وقت الإنشاء الافتراضي.
- ‏⁦`updatedAt @updatedAt`⁩: Prisma تدير وقت آخر تحديث عند استخدام Prisma Client.

‏الـmodel الفعلي فيه علاقات أيضًا، هنشرحها بعد قليل. ملاحظة: الـid في مشروعنا UUID نصي، فالأرقام اللي استخدمناها سابقًا مثل ⁦`12`⁩ كانت لتوضيح توجيه الطلب فقط وليست مثالًا على ID منتج فعلي في هذا المشروع.

‏**فكر:** لو لم نرسل ⁦`stock`⁩ عند الإنشاء، ما قيمته الافتراضية؟ وماذا تعني ⁦`?`⁩ في ⁦`imagePath`⁩؟

## ‏4. رحلة قراءة منتج واحد

‏في ⁦`src/modules/products/products.controller.ts`⁩، الـcontroller يأخذ ⁦`id`⁩ من الطلب وينادي الـservice. الـservice في ⁦`products.service.ts`⁩ تنادي الـrepository:

```ts
const product = await productsRepository.findById(id);
return product ? toProductResponseDto(product) : undefined;
```

‏والـrepository في ⁦`products.repository.ts`⁩ تنفذ:

```ts
export function findById(id: string) {
  return prisma.product.findUnique({
    where: { id },
    select: productResponseSelect,
  });
}
```

- ‏⁦`prisma.product`⁩: التعامل مع Product من العميل المُولَّد.
- ‏⁦`findUnique`⁩: ابحث بقيمة حقل فريد؛ ⁦`id`⁩ فريد لأنه المفتاح الأساسي.
- ‏⁦`where: { id }`⁩: شرط البحث. معناها نفسها ⁦`where: { id: id }`⁩.
- ‏⁦`select`⁩: اختر الحقول التي ستعود من قاعدة البيانات.
- ‏لا يوجد منتج مطابق؟ النتيجة ⁦`null`⁩. الـservice تحولها إلى ⁦`undefined`⁩، والـcontroller يرد بـ404.

‏الاختيار الحقيقي يطلب ⁦`id`⁩, ⁦`name`⁩, ⁦`price`⁩, ⁦`stock`⁩, ⁦`imagePath`⁩. بعدها الـmapper ينشئ شكل الرد، ويحوّل ⁦`price`⁩ إلى رقم ويضع ⁦`imagePath`⁩ تحت اسم ⁦`imageUrl`⁩. اختيار الأعمدة يحصل في الاستعلام؛ تشكيل رد الـAPI يحصل بعده.

‏**تجربة قراءة فقط:** افتح ⁦`products.repository.ts`⁩ وحدد تعريف ⁦`productResponseSelect`⁩، ثم قارن حقوله مع ⁦`toProductResponseDto`⁩ في ⁦`products.mapper.ts`⁩. أي حقل تغير اسمه؟ لا تحتاج لتشغيل أو تعديل شيء.

## ‏5. عمليات القراءة والكتابة

‏هذه أساليب موجودة فعلًا في repository المنتجات:

```ts
prisma.product.create({ data });
prisma.product.update({ where: { id }, data });
prisma.product.delete({ where: { id } });
```

‏⁦`create`⁩ ينشئ صفًا من القيم في ⁦`data`⁩. ⁦`update`⁩ يحدد صفًا فريدًا بـ⁦`where`⁩ ويعدل القيم المرسلة. ⁦`delete`⁩ يحذف الصف المحدد. التعديل والحذف قد يفشلان إذا لم يوجد الصف، والحذف قد يفشل أيضًا بسبب قيود العلاقات. التعامل مع أخطاء Prisma يحتاج مراجعة الكود الذي يستدعي العملية، مش افتراض إن كل فشل معناه 404.

‏⁦`findMany`⁩ يرجع مجموعة قد تكون فاضية، و⁦`count`⁩ يرجع عدد السجلات المطابقة. هذه تختلف عن ⁦`findUnique`⁩ التي ترجع سجلًا واحدًا أو ⁦`null`⁩.

‏**فكر:** لو عايز عدد المنتجات المطابقة لفلتر، هل أنسب تقرأ العدد بـ⁦`count`⁩ أم تفترض إن ⁦`findUnique`⁩ ترجع قائمة؟

## ‏6. الفلترة والترتيب والصفحات

‏في ⁦`findPage`⁩ داخل ⁦`products.repository.ts`⁩ الاستعلام الفعلي يتضمن:

```ts
return prisma.product.findMany({
  select: productResponseSelect,
  orderBy,
  where,
  skip: options.offset,
  take: options.limit,
});
```

‏⁦`where`⁩ يحدد المطابقة، مثل الاسم أو مدى السعر. ⁦`orderBy`⁩ يحدد الترتيب، مثل السعر تصاعديًا. ⁦`skip`⁩ يتجاوز عددًا من النتائج، و⁦`take`⁩ يحد عدد النتائج المرجعة. هذا يسمى pagination: تقسيم النتائج لصفحات بدل إرجاعها كلها. ⁦`count`⁩ في المشروع يستخدم نفس الفلاتر لحساب العدد الإجمالي، بشكل منفصل عن صفحة النتائج.

‏مثال: بعد الترتيب، ⁦`skip: 10`⁩ و⁦`take: 5`⁩ يعني تجاهل أول عشرة وإرجاع حتى خمسة بعدها. الترتيب مهم لتفسير الصفحات. صفحة النتائج والعدد هنا استعلامان منفصلان، وليسا لقطة ثابتة مضمونة إذا تغيرت البيانات بينهما.

‏**فكر:** ما الفرق بين عدد النتائج في الصفحة وبين العدد الإجمالي المطابق للفلتر؟

## ‏7. العلاقات بين الجداول

‏الطلب الواحد يحتوي عدة عناصر. من الـschema:

```prisma
model Order {
  id    String      @id @default(uuid())
  items OrderItem[]
  // حقول أخرى موجودة في الملف الأصلي
}

model OrderItem {
  orderId String
  order   Order @relation(fields: [orderId], references: [id], onDelete: Cascade)
  // حقول أخرى موجودة في الملف الأصلي
}
```

‏هذه مقتطفات وليست models كاملة. ⁦`orderId`⁩ يخزن معرف الطلب المرتبط بالعنصر. ⁦`@relation`⁩ يربط هذا الحقل بـ⁦`Order.id`⁩. و⁦`items`⁩ تتيح الوصول للعناصر المرتبطة من جهة الطلب. ⁦`onDelete: Cascade`⁩ تعني أن حذف الطلب في قاعدة البيانات يحذف عناصره المرتبطة وفق قيد العلاقة؛ لذلك افهم أثر الحذف قبل تجربته.

‏في ⁦`orders.service.ts`⁩:

```ts
const orderToConfirm = await tx.order.findUnique({
  where: { id: orderId },
  include: { items: true },
});
```

‏⁦`include`⁩ تطلب إرجاع عناصر الطلب مع الطلب. الفرق العملي عن ⁦`select`⁩: ⁦`select`⁩ يحدد الحقول المراد إرجاعها، بينما ⁦`include`⁩ يضيف العلاقات المطلوبة إلى نتيجة السجل. طريقة تنفيذ الاستعلام داخليًا تعتمد على Prisma والإعدادات؛ لا نفترض عدد استعلامات SQL من شكل السطر فقط.

‏**فكر:** أي حقل في ⁦`OrderItem`⁩ يحمل معرف الطلب المرتبط؟

## ‏8. ما الفرق بين schema وmigration وgenerate؟

‏تخيل إنك عايز تضيف حقلًا: الـschema يصف الشكل المطلوب، لكن قاعدة البيانات الحالية لا تتغير فقط بحفظه. الـmigration ملف SQL يمثل تغييرًا يمكن تطبيقه على قاعدة البيانات. مجلد ⁦`prisma/migrations`⁩ عندنا يحتوي تاريخًا فعليًا لهذه التغييرات.

‏أول migration مثلًا يحتوي ⁦`CREATE TABLE "public"."Product"`⁩؛ هو تاريخ إنشاء الجدول وقتها، وليس بالضرورة وصفه الحالي، لأن migrations لاحقة أضافت تغييرات.

‏⁦`prisma generate`⁩ يولد أو يحدث Prisma Client من الـschema؛ هو لا يطبق migration على قاعدة البيانات. ⁦`prisma migrate dev`⁩ مخصص لتطوير migrations محليًا وقد يطلب إجراءات مؤثرة على قاعدة التطوير حسب حالتها. ⁦`prisma migrate deploy`⁩ يطبق migrations الموجودة على قاعدة البيانات المستهدفة. تحقق دائمًا من ⁦`DATABASE_URL`⁩ والبيئة والأثر قبل تشغيل أوامر تعدل البيانات. لا تشغل reset أو تحذف بيانات للتجربة دون فهم الأثر وأخذ موافقتك.

‏**تجربة آمنة للقراءة:** افتح ⁦`prisma/migrations/20261008143702_init/migration.sql`⁩ وقارن أعمدة Product فيه مع الـschema الحالي. لماذا قد يختلفان؟

## ‏9. Transaction من تأكيد الطلب

‏الـtransaction مجموعة تغييرات على قاعدة البيانات نريد اعتمادها معًا أو التراجع عنها معًا عند فشلها. في ⁦`orders.service.ts`⁩:

```ts
const result = await prisma.$transaction(async (tx) => {
  // قراءة الطلب والتحقق منه
  // خصم المخزون وتسجيل الحركة وتأكيد الطلب وحفظ الحدث
});
```

‏هذه التعليقات تلخيص لما داخل الدالة وليست نسخة حرفية من الكود. ⁦`tx`⁩ عميل للعمليات داخل نفس المعاملة؛ عملياتها في المشروع تشمل تحديث المخزون وإنشاء حركات المخزون وتأكيد الطلب وحفظ حدث Outbox. لو رُمي خطأ قبل نجاح المعاملة، تتراجع تغييرات قاعدة البيانات داخلها. الـtransaction لا تتراجع تلقائيًا عن إرسال إيميل أو أي عملية خارج قاعدة البيانات.

‏داخلها سطر مهم حقيقي:

```ts
const updated = await tx.product.updateMany({
  where: { id: item.productId, stock: { gte: item.quantity } },
  data: { stock: { decrement: item.quantity } },
});
```

‏التحديث يشترط المنتج والمخزون الكافي في نفس العملية، ويخصم الكمية. ⁦`updated.count`⁩ يخبرنا كم صفًا تحدّث؛ إذا كان صفرًا، الكود يرمي خطأ ويوقف تأكيد الطلب. وضع الشرط والخصم في تحديث واحد يساعد في منع بيع مخزون غير كافٍ مع طلبات متزامنة. تفاصيل التزامن الأوسع تستحق مراجعة منفصلة، خصوصًا لو طلبان يحاولان تأكيد نفس الطلب.

‏**فكر:** لو خصمنا المخزون ثم فشل تسجيل الحركة داخل نفس transaction، هل نريد حفظ الخصم وحده؟

## ‏10. Index باختصار

‏الـindex بنية إضافية في قاعدة البيانات تساعدها أحيانًا على العثور على البيانات أو ترتيبها بسرعة؛ لها تكلفة تخزين وتحديث، وليست ضمانًا أن كل استعلام سيستخدمها.

‏في ⁦`InventoryMovement`⁩ عندنا:

```prisma
@@index([productId, createdAt])
@@index([productId, createdAt, id])
```

‏الترتيب هنا مرتبط بالبحث عن حركات منتج وترتيبها. الكود يوضح أن الثاني يساعد ترتيب cursor pagination. لا نحكم على الفائدة أو نحذف index بالتخمين؛ نراجع خطة الاستعلام والقياسات أولًا.

## ‏11. تتدرب إزاي؟

‏ابدأ بالقراءة فقط، خطوة واحدة كل مرة:

1. ‏افتح ⁦`prisma/schema.prisma`⁩ واقرأ ⁦`Product`⁩. اشرح لنفسك الفرق بين ⁦`String?`⁩ و⁦`String`⁩.
2. ‏افتح ⁦`products.repository.ts`⁩ وتتبع ⁦`findById`⁩، ثم ارجع للـservice والـmapper والـcontroller. اكتب لنفسك ماذا يحدث إذا لم يجد منتجًا.
3. ‏اقرأ ⁦`findPage`⁩ وحدد الفلتر والترتيب والصفحة. توقع أثر ⁦`skip`⁩ و⁦`take`⁩ بأرقام صغيرة.
4. ‏اقرأ علاقة ⁦`Order`⁩ و⁦`OrderItem`⁩، وحدد مكان المفتاح الذي يربطهما.
5. ‏اقرأ transaction تأكيد الطلب، وحدد ما يجب أن يُحفظ معًا وما يحصل عند خطأ المخزون.

‏لو احتجت تجربة على بيانات فعلية، افحص البيئة أولًا واستخدم بيانات تجريبية. لا تحذف containers أو volumes أو سجلات، ولا تشغّل migrations أو reset، قبل فهم الأثر والتأكد منك.

## ‏12. أسئلة تراجع بها نفسك

1. ‏ما الفرق بين PostgreSQL وPrisma Client؟
2. ‏هل حفظ schema يغير قاعدة البيانات وحده؟ وما وظيفة generate؟
3. ‏ماذا ترجع ⁦`findUnique`⁩ إذا لم تجد صفًا؟
4. ‏لماذا نستخدم ⁦`select`⁩؟ وما وظيفة الـmapper بعده؟
5. ‏ما الفرق بين ⁦`where`⁩ و⁦`data`⁩ في ⁦`update`⁩؟
6. ‏كيف يعرف ⁦`OrderItem`⁩ الطلب المرتبط به؟
7. ‏لماذا يحتاج تأكيد الطلب إلى transaction؟ وما حدودها خارج قاعدة البيانات؟

‏لو سؤال واقف معاك، ارجع للجزء المرتبط به وجرب تشرح الإجابة باستخدام اسم ملف وسطر من مشروعك.

## ‏13. إضافة Prisma إلى مشروع جديد

‏المشروع الحالي فيه Prisma بالفعل. الخطوات التالية للتعلّم أو لمشروع جديد؛ لا تعيد تهيئة مشروعنا ولا تنفذها على قاعدة بيانات مهمة. المشروع يستخدم Prisma 6، لذلك أمثلته وإعداداته خاصة بهذا الإصدار، وقد تختلف خطوات الإصدارات الأخرى.

‏في مشروع TypeScript جديد نحتاج الحزم التالية: حزمة CLI للتوليد والـmigrations، وعميل التشغيل للتطبيق. مثال تعليمي مع نفس الإصدار الرئيسي المستخدم هنا:

```powershell
npm install @prisma/client@6
npm install --save-dev prisma@6
npx prisma init --datasource-provider postgresql
```

‏الأول يضيف عميل التشغيل، والثاني أدوات التطوير، والثالث ينشئ ملفات إعداد أولية؛ قد يرفض أو يتعارض مع ملفات موجودة. بعد ذلك نضبط عنوان اتصال تجريبي في متغير ⁦`DATABASE_URL`⁩، ونكتب الـmodels في schema، وننشئ migration في قاعدة تطوير مخصصة، ثم نتأكد من توليد العميل. لا تضع بيانات الاتصال الحقيقية في Git.

‏في مشروعنا عندك فعلًا ⁦`prisma/schema.prisma`⁩ و⁦`src/database/prisma.ts`⁩ والـdependencies في ⁦`package.json`⁩. لا تحتاج الأوامر السابقة لمجرد تشغيل المشروع الحالي.

### ‏عنوان الاتصال من جهازك ومن Docker

‏الـPostgreSQL في Compose ينشر المنفذ 5433 على الجهاز، بينما منفذ الخدمة داخل شبكة Compose هو 5432. لذلك من الجهاز نستخدم ⁦`localhost:5433`⁩، ومن حاوية أخرى في نفس شبكة Compose نستخدم اسم الخدمة ⁦`postgres:5432`⁩. كلمة ⁦`localhost`⁩ دائمًا تعني البيئة التي ينفذ فيها البرنامج نفسه. تأكد من المستخدم والقاعدة والقيم عندك قبل أي اتصال.

‏**فكر:** لو تطبيق Node يعمل في container، هل ⁦`localhost`⁩ يقصد جهازك أم الـcontainer نفسه؟

## ‏14. تدريب متكامل على إضافة حقل

‏هذا سيناريو تعليمي فقط: نريد إضافة وصف اختياري للمنتج. لا تعدل المشروع الآن؛ افهم التسلسل أولًا. على قاعدة تطوير منفصلة، أضف للـmodel:

```prisma
description String?
```

‏علامة الاستفهام تسمح للمنتجات القديمة بعدم وجود وصف. بعد مراجعة الـschema وتحديد قاعدة التطوير المقصودة، يمكن إنشاء migration باسم مفهوم:

```powershell
npx prisma migrate dev --name add_product_description
```

‏الأمر ينشئ migration اعتمادًا على الفرق ويطبقها على قاعدة التطوير؛ وقد يطلب reset أو يكشف مشكلة drift، فلا توافق تلقائيًا لأن reset يمسح البيانات. راجع ملف SQL الناتج ونتيجة الأمر. قد يستخدم Prisma قاعدة ظل مؤقتة لمقارنة تاريخ migrations. ثم تأكد أن العميل محدث؛ المشروع يوفر ⁦`npm run prisma:generate`⁩ لتوليده. لا تجعل إضافة الحقل للـAPI ضمنية: لو أردنا استقبال الوصف أو إظهاره فعلينا تعديل validation والأنواع والاستعلام والـmapper حسب المطلوب.

‏إضافة حقل في schema ليست إضافة ميزة كاملة في API. تغيير schema وmigration وclient وكود التطبيق خطوات منفصلة تتعاون معًا.

‏**فكر:** لو أضفنا ⁦`description`⁩ في schema فقط، لماذا قد لا يظهر في رد المنتج الحالي؟ راجع ⁦`productResponseSelect`⁩ والـmapper.

## ‏15. migration معقدة بدون خسارة البيانات

‏المشكلة: جدول فيه بيانات قديمة، ونريد إضافة حقل مطلوب مثل ⁦`sku`⁩، وهو كود مميز لكل منتج. لو أضفت عمودًا مطلوبًا بلا قيمة للصفوف القديمة، قد تفشل migration. ولو وضعت نفس القيمة الافتراضية لكل الصفوف ثم أضفت شرط uniqueness، ستفشل عند وجود أكثر من صف.

‏الحل التعليمي يعتمد على مراحل، وكل مرحلة تحتاج مراجعة واختبار على نسخة بيانات مناسبة:

1. ‏**توسيع:** أضف ⁦`sku`⁩ اختياريًا أولًا، وانشر تطبيقًا يفهم وجوده أو غيابه ويكتب القيمة للمنتجات الجديدة.
2. ‏**ملء البيانات القديمة:** جهز backfill، يعني عملية تملأ القيم القديمة بقيم صحيحة وفريدة. اختبرها أولًا على بيانات ممثلة للواقع، وصممها لتستأنف بأمان لو توقفت. التوليد يجب أن يحترم قواعد النشاط، وليس أرقامًا نفترض صلاحيتها.
3. ‏**تحقق:** افحص القيم الفارغة والتكرارات قبل فرض القيود. هذا فحص قراءة فقط، لكنه يجب أن يعمل على قاعدة التطوير المقصودة:

```sql
SELECT COUNT(*) FROM "Product" WHERE "sku" IS NULL;
SELECT "sku", COUNT(*) FROM "Product"
WHERE "sku" IS NOT NULL
GROUP BY "sku" HAVING COUNT(*) > 1;
```

4. ‏**فرض القواعد:** بعد نجاح التحقق وتأكد أن كل النسخ تكتب ⁦`sku`⁩، أضف قيد uniqueness وجعله مطلوبًا عبر migration مدروسة. اختبر الفشل، مدة التنفيذ، الأقفال وخطة الرجوع أولًا.
5. ‏**تنظيف:** بعد التأكد أن النسخ القديمة لا تحتاج التوافق، أزل الكود المؤقت في تغيير لاحق.

‏هذه ليست migration جاهزة للتطبيق على مشروعنا؛ ⁦`sku`⁩ غير موجود في الـschema الحالي. أثناء rolling deployment قد تعمل نسختان من التطبيق في وقت واحد، لذا يجب أن تتوافق كل مرحلة مع النسختين. على جدول كبير حتى إنشاء index أو فرض قيد قد يسبب انتظارًا أو ضغطًا؛ اختبر على بيئة مشابهة وراجع أسلوب PostgreSQL المناسب قبل التنفيذ.

‏إذا احتجت SQL مخصصًا، يمكنك في قاعدة تطوير مخصصة استخدام ⁦`npx prisma migrate dev --name ... --create-only`⁩ لإنشاء ملف migration دون تطبيقه، ثم مراجعته وتعديله واختباره قبل التطبيق. حتى إنشاء الملف يغير ملفات المشروع، وليس أمر قراءة فقط. migrations المطبقة لا تعدل تاريخها بشكل عشوائي؛ عالج الأخطاء في بيئة مناسبة وبخطة واضحة. ⁦`migrate deploy`⁩ يطبق الملفات الموجودة ولا يضمن وحده إصلاح اختلافات غير متوقعة بين schema والقاعدة.

‏**فكر:** لماذا لا نفرض أن ⁦`sku`⁩ مطلوب وفريد قبل ملء بيانات المنتجات القديمة؟

## ‏16. قراءة index وفهم متى يفيد

‏تخيل جدول حركات مخزون كبيرًا، وتريد أحدث حركات منتج معين. لو كان عندك فهرس مناسب، PostgreSQL قد تستخدمه لتصل لصفوف المنتج وتساعدها في الترتيب بدل فحص كل الجدول؛ القرار فعليًا يتوقف على حجم البيانات والإحصاءات وخطة الاستعلام.

‏في مشروعنا migration موجودة باسم ⁦`20261014110000_add_inventory_movement_cursor_index`⁩:

```sql
CREATE INDEX "InventoryMovement_productId_createdAt_id_idx"
ON "InventoryMovement"("productId", "createdAt", "id");
```

‏أول عمود ⁦`productId`⁩ مناسب لفلترة حركات منتج، ثم ⁦`createdAt`⁩ و⁦`id`⁩ مرتبطان بالترتيب والـcursor. ترتيب الأعمدة مؤثر؛ هذا ليس فهرسًا سحريًا لكل بحث ممكن. الفهرس الإضافي يستهلك مساحة ويحتاج تحديثًا مع الكتابة. في المشروع الفهرس القديم ⁦`[productId, createdAt]`⁩ ما زال موجودًا؛ التعليق يقول الاحتفاظ به لحين وجود قياسات كافية، لا أنه يجب حذفه.

‏الـindex العادي يسرع بعض الاستعلامات لكنه لا يمنع التكرار. ⁦`@unique`⁩ و⁦`@@unique`⁩ يفرضان عدم تكرار القيم وفق القيد. في ⁦`IdempotencyKey`⁩ يوجد ⁦`@@unique([scope, key])`⁩، أي الزوج معًا فريد؛ يمكن تكرار ⁦`key`⁩ في ⁦`scope`⁩ مختلف. قياس الاستعلام يتم بخطة PostgreSQL مثل ⁦`EXPLAIN`⁩ على بيئة مناسبة؛ ⁦`EXPLAIN ANALYZE`⁩ ينفذ الاستعلام فعلًا، فاحذر إذا كان استعلام كتابة.

## ‏17. تفاصيل transactions والتزامن

‏في مثال الطلب، إنشاء الطلب وعناصره وسجل مفتاح idempotency يحدث داخل transaction. تأكيد الطلب في transaction أخرى يخصم المخزون ويسجل الحركة ويحدث حالة الطلب ويحفظ حدث outbox. إذا رمى الكود خطأ داخل المعاملة تتراجع تغييراتها في قاعدة البيانات؛ بعدها يقرر التطبيق كيف يتعامل مع الخطأ.

```ts
const updated = await tx.product.updateMany({
  where: { id: item.productId, stock: { gte: item.quantity } },
  data: { stock: { decrement: item.quantity } },
});
```

‏لو المخزون 5 وطلبان مختلفان يريد كل منهما 4، الشرط والخصم في تحديث واحد يساعدان على ألا يخصم الطلب الثاني من مخزون لم يعد كافيًا. مجرد قراءة 5 في التطبيق ثم كتابة 1 لاحقًا من كل طلب قد يسبب نتيجة خاطئة. لكن transaction وحدها لا تحل كل سباقات العمل: تأكيد الطلب نفسه من طلبين في نفس الوقت يحتاج تحليلًا مستقلًا لطريقة قفل الصف أو التحديث المشروط والحالة. لا نستنتج من المثال ضمانًا شاملًا لكل سيناريو تزامن.

‏الـisolation level يعني قواعد ما يمكن للمعاملات المتزامنة رؤيته من تغييرات بعضها. الـdeadlock يحدث عندما تنتظر معاملات أقفالًا تحتفظ بها معاملات أخرى في دائرة؛ ترتيب تحديث المنتجات في المشروع يقلل خطره ولا يلغيه. بعض أخطاء التزامن تستدعي إعادة محاولة مدروسة، مع التأكد أن العملية قابلة للإعادة بأمان. لا تبقِ transaction مفتوحة أثناء اتصال شبكة بطيء أو إرسال إيميل؛ المعاملة لا تضمن التراجع عن خدمة خارجية. الـoutbox في المشروع يحفظ حدثًا داخل المعاملة لمعالجته لاحقًا.

## ‏18. تشخيص المشاكل بدل حفظ الأوامر

- ‏اتصال فشل: أين يعمل التطبيق؟ هل عنوان ⁦`DATABASE_URL`⁩ مناسب لهذه البيئة؟ هل PostgreSQL جاهزة والبيانات والصلاحيات صحيحة؟ لا تنشر كلمة المرور.
- ‏عمود مفقود: قارن الـschema والـmigration المطبقة وقاعدة البيانات المستهدفة، ثم تأكد أن التطبيق متصل بالقاعدة الصحيحة.
- ‏TypeScript لا يرى حقلًا جديدًا: افحص schema وتوليد Prisma Client واستيراده، ثم أعد فحص الأنواع. توليد العميل لا يطبق تغييرات القاعدة.
- ‏تعارض فريد: ابحث عن القيد والبيانات المكررة؛ في إنشاء الطلب المشروع يتعامل مع ⁦`P2002`⁩ لمفتاح idempotency، لكنه يتحقق أيضًا أن السجل المتوقع موجود وأن الطلب له نفس المحتوى.
- ‏عملية بطيئة: افحص شروط الاستعلام وحجم النتائج والترتيب وخطة التنفيذ قبل افتراض أن index جديد هو الحل.

‏ابدأ دائمًا بتحديد البيئة والعملية المتأثرة. لا تستخدم reset أو تحذف بيانات كخطوة تشخيص افتراضية.

## ‏19. نفهم الـmodels من رحلة الطلب

‏خلّينا نبدأ بمشكلة من المشروع: مستخدم يريد شراء منتجين. نحتاج نعرف مين عمل الطلب، وإيه المنتجات والكميات، وسعر كل منتج وقت إنشاء الطلب. في ملف `prisma/schema.prisma` عندنا models حقيقية لكل جزء:

```text
User      المستخدم الذي أنشأ الطلب
Order     الطلب نفسه وحالته وإجماليه
OrderItem عنصر واحد داخل الطلب
Product   المنتج الموجود في الكتالوج والمخزون
```

‏كلمة model تعني وصف نوع البيانات وعلاقاته في Prisma. الـmodel مش هو الـmodule: مجلد `src/modules/orders` يجمع كود ميزة الطلبات، أما `model Order` في الـschema فيصف بيانات الطلب.

### ‏مين صاحب الطلب؟

```prisma
createdById String
createdBy User @relation(fields: [createdById], references: [id])
```

‏السطران من `model Order`. الأول حقل يخزّن معرف المستخدم. الثاني يعرّف العلاقة: قيمة `createdById` تشير إلى `id` في `User`. وفي `User` يوجد `orders Order[]` للوصول لطلبات المستخدم. يعني مستخدم واحد يمكن أن ينشئ عدة طلبات، وكل طلب له مستخدم أنشأه.

### ‏إيه الموجود داخل الطلب؟

```prisma
items OrderItem[]
```

‏السطر من `model Order`. علامة `[]` تعني مجموعة عناصر. كل `OrderItem` فيه `orderId` للطلب و`productId` للمنتج و`quantity` للكمية. وفيه `productName` و`unitPrice`: نسخ من الاسم والسعر وقت إنشاء الطلب، حتى لو سعر المنتج تغير بعد ذلك.

‏في `src/modules/orders/orders.service.ts` الكود يقرأ المنتجات من قاعدة البيانات ويجهز العناصر من السعر والاسم الموجودين عندنا، بدل ما يعتمد على السعر المرسل من العميل. بعد ذلك ينشئ الطلب وعناصره:

```ts
const order = await tx.order.create({
  data: { createdById, total, items: { create: items } },
  include: { items: true },
});
```

‏`tx.order.create` ينشئ الطلب داخل transaction. `createdById` صاحب الطلب و`total` إجماليه. `items: { create: items }` ينشئ عناصر مرتبطة بالطلب؛ ده اسمه nested write، يعني كتابة بيانات مرتبطة من خلال عملية واحدة. `include` يطلب إرجاع العناصر مع الطلب الناتج. كل ده داخل transaction أوسع تشمل تسجيل مفتاح idempotency؛ إذا فشلت المعاملة تتراجع تغييرات قاعدة البيانات داخلها.

**‏فكر:** لو سعر المنتج اتغير بكرة، أي حقل نرجع له لمعرفة سعره وقت إنشاء الطلب: `Product.price` ولا `OrderItem.unitPrice`؟

### ‏ربط الطلب بالمخزون

‏إنشاء الطلب في المشروع يبدأ بحالة `DRAFT`، يعني مسودة. عند تأكيده، الكود يقرأ عناصره، ويتحقق من توفر المخزون، ثم يسجل كل تغيير في `InventoryMovement` ويحدّث حالة الطلب داخل transaction. الـmovement سجل يخبرنا كيف تغير المخزون ولأي سبب، وليس المخزون الحالي نفسه. المخزون الحالي في `Product.stock`.

‏افتح الملفات بالترتيب ده وانت بتتبع المثال: `prisma/schema.prisma` للعلاقات، ثم `src/modules/orders/orders.router.ts` للمسارات، ثم `orders.controller.ts` و`orders.service.ts` لرحلة الطلب. لا تحتاج تعديل أي ملف أو تشغيل أمر في الخطوة دي.
